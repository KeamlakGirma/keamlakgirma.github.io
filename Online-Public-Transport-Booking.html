Why four apps

Booking a ride is only one side of running a transit system.

A rider app that generates tickets is only useful if someone downstream can act on that ticket. This project treats booking as one step in a longer chain — a ticket has to reach a driver, a route has to reach an agent's map, and a rider's complaint has to reach someone who can read it.

So instead of one client and a database, this is two React Native apps (rider, driver) and two React web apps (admin, agent) sitting on top of one Express + MongoDB API — with real JWT sessions, password hashing, and Cloudinary‑hosted profile photos, not placeholder auth.

Engineering notes

What's solid, and what's next

Written the way I'd walk a reviewer through the repo — including the parts that are still rough.

01

Rider & driver auth is production‑shaped

Passwords hash on save via a Mongoose pre‑save hook, sign‑in issues a JWT and appends it to a rotating token list (pruned after 24h), and sign‑out removes just that token — a real session model, not a stub.

02

The admin/agent API needs a live database

The rider/driver side connects to MongoDB Atlas, but the admin/agent entry point still has a placeholder connection string — that half of the API isn't hooked up to a live database in this snapshot.

03

Keys and env names need to line up

A Mapbox token and a Google Maps key are inline in the client source rather than read from environment variables, and the admin model expects JWTPRIVATEKEY while the server's .env defines JWT_SECRET — rotating the keys and reconciling the variable names is the first hardening pass.
